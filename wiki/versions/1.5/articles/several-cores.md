---
title: Using several cores
category: Game rules
---
From 1.5 the simulation can use several of your computer's cores at once. Besides the thread the simulation already runs on, the [[page:world-server]] starts **region workers**: more threads, each holding a whole copy of the world. When the simulation is busy, the mobs' and villagers' thinking for each tick is shared out between them, a village (with its villagers, its animals and its horses) or a region of the wild at a time, and every worker then takes in what the others decided, so all the copies stay the same.

## How many

By default the game starts none: the simulation runs on its one thread. Region workers cost a core each even when they aren't needed (while one thinks, every other one replays every tick to keep its copy up to date), and splitting hasn't yet made the game faster, so they start only when you ask, until clusters (below) take over.

- `./run.sh --workers <n>` (or `run.cmd --workers <n>`) sets the number for the [[page:world-server]], counting the simulation's own thread: `--workers 4` starts 3 more. `--workers 1` (the default) is none.
- On the world server's page, adding `?workers=<n>` to the game's address does the same for that visit.
- The pause menu's **Distant villages** panel has a **Cluster workers** line: *1 (clusters off)* (the default for now), *Automatic*, or 2 to 16. *Automatic* is one worker per performance core, and the line shows the number it would use. The world server works it out for its own computer: Apple's performance cores on a Mac, the performance cores on an Intel hybrid chip under Linux, and the physical cores elsewhere (half the logical CPUs on Windows). More than one worker splits the world's clusters (below) between them. On Linux, when the computer has fast and slower cores (AMD's Zen 5 and Zen 5c, Intel's P and E cores), the world server keeps its simulation thread on the fast cores and the other workers on the slower ones, if there is a slower core for each. On Gordon's laptop that ran about 8% faster than leaving it to the system. The [[page:game-log]] says where they went. `./run.sh --no-pin` turns this off. The setting applies from the next world you start. `--workers` on the command line, or `?workers=` in the address, overrides it, and the line then says so. Each change is an INFO line in the [[page:game-log]].
- Only the world server has region workers. When the simulation runs in the browser (in a worker or in the page: see [[page:performance-meter]]), it runs on one thread, the *Cluster workers* line reads *1 (world server only)*, and F3 says why.

## When it splits

Splitting a tick between threads costs time of its own: every worker sends the others what its mobs did, and waits for them. With a village or two loaded, one thread is faster, so the game only splits when it would help:

- While the simulation keeps up with the speed you chose, one worker thinks for everything and the others just follow along, replaying the same ticks to keep their copies up to date.
- When ticks have been dropped for 2 seconds (fast-forward asking for more than the machine gives), the game tries the split for 200 ticks. If ticks got at least 10% faster it keeps it; if not, it goes back to one and waits before trying again (longer each time it didn't pay).
- At normal speed (1x) the game also tries the split once the simulation has needed 65% of each second for 30 seconds, or less when the [[page:village-loading|Distant villages]] limit is lower and is holding villages back. While it tries, no more distant villages join, so the trial compares like with like. With clusters, a split that doesn't pay stops the other workers until the world is next loaded.
- A split starts only once the followers have caught up. A follower on a slower core than the first worker (the world server puts the first on the fastest cores) would fall further behind every second, so while one thinks, the first worker waits whenever the followers are more than about a second of its ticks behind: the game then goes at the followers' pace until it splits. The [[page:game-log]] says so once a world (INFO, kind *workers*).
- `?split=always` or `?split=never` on the address (`./run.sh --split always|never` for the server) overrides that, for testing and measuring.

Whether it splits or not, the world plays exactly the same: the same mobs do the same things on the same ticks with 1, 2 or 8 workers (the tests compare the [[page:state-hash]] after a game day with each). While split, the copies are compared every 5 game minutes; if they ever differ, the game logs an error and goes on with one worker.

## Where it shows

- **F3**: a line starting `Workers`. With one worker thinking it says how many follow and how far behind they are, for example `Workers 3: one thinks (2/2 followers ready, 0 ticks behind; 9.9 ms a tick, splits when ticks drop or the load stays high)`. Split, it gives the regions and mobs each worker had and the milliseconds of each part of a tick: `Workers 2: regions 19/1, mobs 136/71  think 4.3  exchange 11.1  rest 4.0 ms`.
- **Debug screen**: the **Workers** card shows the same, per worker.
- **Debug screen, Threads card**: how busy each of the game's threads is: the page (drawing and input), the simulation, each region worker, and the debug server (or the world server's main thread). Each bar is the share of the last minute the thread spent working, with the last second in brackets; time a worker spends waiting for the others at the end of a split tick doesn't count. The page's row also gives its frames a second and the milliseconds of work in each frame, with how many of those were the drawing call: a page near 100% with most of each frame in drawing is waiting on the graphics card (a screen refreshing 120 or 165 times a second asks for that many frames), not on the game's own work. A browser can't tell which core a thread runs on, so below the threads the card draws one bar per core of the computer the debug server runs on, as the operating system reports it (green under half busy, yellow, then red over 85%), with a white tick for each core's average over the last minute. With many workers the card is taller than the others at the top of the debug screen; it scrolls inside its box rather than stretching its row.
- **Debug screen, Mobs map**: with **Regions** on, each region is coloured by the worker that thinks for its mobs, shaded darker the more mobs it holds. Workers aren't strictly split by land: a village's villagers, pen animals and golems all think on the village's worker wherever they stand, while wild animals and monsters go by the region they're in, so a region can hold mobs of more than one worker. Such a region is drawn in stripes, one band per worker, each as tall as its share of the region's mobs. Each village is outlined in its worker's colour and named with it. The legend under the map names each worker's colour, how many regions it has most of the mobs in, and how busy its thread is; the colours match the Threads card. With one worker thinking, every region is the simulation's colour.
- **[[page:world-server|Pause menu]]**: the *Simulation* button says `World server (N threads)`.
- **[[page:game-log]]**: INFO lines (kind *workers*) say how many workers a world got, when they are ready, when the thinking is split and whether the split paid. An ERROR says if a worker crashed or the copies stopped matching. A worker's own ERROR lines (a villager it was running got stuck, say) come into the same log, marked *worker 2:* and so on, up to 20 a game hour from each.

## If a worker crashes

While the thinking is split, a worker that crashes stops the simulation: the game shows the error and offers to reload from your last save, as it does for any crash of the simulation, and the error goes to the game log. While one worker is thinking, a follower that crashes is just dropped and the game goes on with one.

Saving is unchanged: the thread that leads holds the whole world between ticks, so it saves as it always did.

## Clusters (in progress)

Region workers never pay off much, because every worker has to keep its whole copy of the world in step every tick. Version 1.5 is moving to **clusters** instead: each village and the land round it (about half the way to the next village) runs on its own, and clusters only pass things to each other every four game seconds, at a *meeting*. Something that crosses from one cluster to another, like a request aimed at a mob over the border, waits for the next meeting, at most four game seconds. That happens on one worker too, so the world plays exactly the same with any number of workers. You never see that wait: every cluster within your view distance (plus 48 blocks, and as far again as you moved since the last meeting, so flying fast pulls the villages ahead in early) runs together with you as one group. New land that loads between two meetings appears at the next one, so while the clusters are split, terrain ahead of you can show up to four game seconds late.

What one cluster may know about another village comes from the *shared table*: at each meeting every simulated village publishes a summary (its prices and the goods it offers, its population), stamped with the moment it describes, and until the next meeting everyone reads that. [[page:caravans|Caravans]] already work this way: a merchant plans its trip from the other village's row in the table, is handed over to the other village's cluster at the meeting after it arrives and trades there, and goes back to its home's cluster at the meeting after it comes home (it waits at the edge of the village for up to two seconds until then). A new trip asks for its place on the road at the next meeting, where at most two are let out, lowest merchant first; which villages are simulated is decided at meetings too.

The groundwork is in the game but off: with it off, the world plays exactly as before. The game's systems (mobs, village life, animals, caravans, blocks) are being moved over one by one. When the clusters are turned on, the [[page:game-log]] notes it, and an ERROR names any cluster whose tick fails.

Moved over so far: the mobs' thinking, and the mobs and wild life around them. With clusters on, each cluster spawns its own monsters in its own chunks (each chunk with the same odds as before), rolls and stores the wild animals of its own chunks, and moves its own dropped items, arrows and boats (a boat goes with the cluster of the mob sitting in it). A cluster away from yours sees you where you were at the last meeting. A wild mob that wanders off the loaded land into a chunk of another cluster waits there until the next meeting, and then that cluster stores it with its chunk.

The world's own ticks already run by cluster: flowing water, crops and sugar cane, saplings, farmland drying out, grass spreading, crops catching up in reloaded chunks, and furnaces and bakers' ovens. Each cluster ticks only its own blocks. A block right at a border, whose tick would look at or change the other cluster's blocks (water flowing over the border, a tree growing across it), waits for the next meeting and is done there, so water still crosses from one cluster to the next, a second at a time. With the clusters on, chunks also arrive and leave only at meetings: a chunk generated in between waits, at most a second, before it appears.

Village life has moved over: builders, jobs, breeding, storage, bakers, explorers, restocking, the day timeline, village stats, foresters and signs each run per cluster, and a village's records belong to its own cluster. A new village is set up at a meeting, which the [[page:game-log]] notes.

The animals have moved over: sheep pens, chicken coops, cow pastures, pig sties, horses and their herds, stables and bees each run with the cluster they belong to (a pen with its village, a horse with where it is or was last seen, a herd with where it was at the last meeting, bees with their home). With the clusters on, two things play a little differently: at most 600 bees are out at once in each cluster rather than in the whole world, and only bees in the player's own cluster follow a flower the player holds (the others are too far away to see it anyway).

To try clusters while you play, add `--clusters` to `./run.sh` along with a number of workers (`./run.sh --workers 4 --clusters`), or `?clusters=1` with `?workers=<n>` to the world server page's address. The split then shares out the clusters instead of the regions' thinking: the group with you in it stays on the first worker, which also serves your page, and the rest go to whichever worker has the least to do. F3 shows each worker's groups and time a tick. If the page can't keep up with what a fast world sends it (a slow machine at 100x), the world server sends the moving mobs and items twice a second instead of every tick until it catches up, and the [[page:game-log]] notes it.

While fast-forwarding with the clusters split, the other workers don't wait for the first worker's ticks between meetings: clusters can't reach each other until the next meeting, so each worker runs its own clusters' ticks as fast as it can and catches up with what the first worker did (your actions, chunks loading) as it arrives. Anything that would change every cluster at once, such as a slash command, waking up in the morning, a change to the monster options or the Distant villages settings, waits for the next meeting (at most 4 game seconds).

When the clusters are split over several workers, a worker keeps only its own clusters' mobs up to date. It sees every other mob where it was at the last meeting, and at a meeting it is sent whole only the mobs that change worker (or that something on it is about to read, like a merchant arriving or a chunk being unloaded). So a meeting sends a short summary of each mob instead of every change to every mob.

A save while the clusters are split waits for the next meeting. There each worker writes down its own mobs' part of the save (where each one is and what it is doing, a villager's trades, a horse's place) and sends just that to the others, so no worker has to be sent every mob whole. The periodic check that the workers' copies of the world still agree (every five game minutes) works the same way: each worker hashes its own mobs. Both take a fraction of a second, where they used to pause the game for about a second with many villages.

## What it costs

Each worker holds a full copy of the world, so each one takes about as much memory as the simulation does on its own. On a machine with little memory, `--workers 1` or a small number is the better choice.
